## 2. Score-normalization and version contract

- Valid = a **JSON number**, finite, within **[0, 100] before rounding**. Numeric strings are rejected: `responseSchema` declares `matchScore: NUMBER`; no compatibility requirement justified accepting strings.
- Rounding: half-up once, `Math.floor(x + 0.5)` (59.5 → 60, 79.49 → 79, 79.5 → 80, 72.5 → 73). Idempotent on its own output (tested 0–100 in 0.25 steps).
- Band: `derivePassProbability(integer)`; thresholds 60/80 and `probabilityVersion = canonical-score-v1` unchanged.
- The same integer goes to the API body, `history.match_score`, `candidate_cvs.match_score`, `analysis_result.matchScore` and the owner's reload (tested on the real stack, 9 boundary values).
- `scoreVersion = 'canonical-en-v2'`: validation and normalization only; same prompt, model and request (not the A2 rubric).
- **Compatibility evidence (migration-free):** `score_version` columns are free text with no CHECK (migrations `20261030000000`); readers test presence only (`AnalysisDetailsTab.tsx:28`, `historyService.ts:50`, `applicationService.ts:59`); `save_candidate_analysis_attempt` copies the result's `scoreVersion`; Excel export and comparison views do not read it; `resolveProbability` keys on `probabilityVersion` only. Legacy and v1 rows are never rewritten (real-DB test: a legacy 82.5/NULL and a v1 NULL row unchanged after new analyses).
- `categoryScores` / `overallAtsParseabilityScore`: still coerced to 0 when malformed and not range-checked. They never feed `matchScore`, quota or persistence integrity; left unchanged (debt §11).

## 4. Invalid AI output contract and quota settlement

| Step | Behaviour |
|---|---|
| Detection | after Gemini returned (definitive); before probability, commit, save, localization |
| Commit | **never** (`commit_analytics_quota*` not called) |
| Release | `release_analytics_quota(p_outcome = 'provider_error')` via the existing bounded `settle()` retries (idempotent RPC) |
| `refunded` (new or replay of a refunded row) | 502, `quotaReleased: true`, copy "…allowance has not been used…" |
| RPC answered another state (e.g. TTL already turned it `uncertain`) | 502, `quotaReleased: false`, unconfirmed copy; no second release |
| No definitive answer (`unknown`) | 502, `quotaReleased: false`, unconfirmed copy; the reservation follows the **existing** TTL → `uncertain` contract (forgiven twice per cycle, then charged) — unchanged |
| Duplicate key after the refund | existing 409 `duplicate_request` with `state: refunded`, no Gemini call (real DB) |
| Concurrent same key | one Gemini call, one 502, one 409 (real DB) |
| Ledger rows | never deleted; no unguarded decrement; usage stays 0 (real DB) |
| Localization | never runs for invalid output (one Gemini call, VI included) |

Messages (server body and client mapping, EN/VI):
- released — EN "The analysis returned an invalid result. Your analysis allowance has not been used. Please try again." / VI "Kết quả phân tích chưa hợp lệ. Bạn chưa bị trừ lượt phân tích. Vui lòng thử lại."
- unconfirmed — EN "…We could not confirm whether your analysis allowance was used. Please check your usage before trying again." / VI "…Chưa xác nhận được việc hoàn lượt phân tích. Vui lòng kiểm tra số lượt đã dùng trước khi thử lại."

No raw model text, CV/JD content or provider detail in the body (privacy test).

## 5. Provider and abuse accounting

- **Provider spend:** the `analysis_log` error row carries the real `input_tokens`, `output_tokens` (candidates + thoughts, counted once), `model`, `latency_ms`; message `[invalid_ai_output:<reason>:release_<refunded|not_refunded|unknown>]` (≤ 15 distinct strings; nothing groups by exact message). **Debt:** `admin_report_stats` sums tokens only for `status = 'success'` (`20261101170000_admin_report_stats.sql:86-104`), so invalid-output spend is recorded but **not shown in the Report tab totals**.
- **Abuse control:** the hourly AI slot (`consume_api_rate_limit`, bucket `ai_analyze`) is consumed before Gemini and never refunded — invalid outputs still count (real DB: 1 hit per request).
- Sentry: `analyze_invalid_ai_output` (warning) with `reason` and `release` tags only.

## 6. Recruiter: ownership-fenced failure

`failCandidateAttempt` updates `status = 'error', error_message = <copy>` **where `id`, `analysis_attempt_id` = this attempt and `status = 'analyzing'`** — the predicate of the browser's `releaseCandidateAnalysis`. The pre-Gemini gate already bound the attempt to this user's campaign.

| Case (real DB unless noted) | Result |
|---|---|
| Current attempt owner | candidate `error`, result/score untouched (NULL), ledger refunded, usage 0 |
| Newer attempt took over during Gemini | fence rejects; newer attempt untouched (`analyzing`) |
| Row completed elsewhere (`done`, 77) | never overwritten |
| Duplicate request with the same attempt | 409, no Gemini call, row stays `error` |
| Batch with valid + invalid | valid `done` 73 (column = JSON), invalid `error`; ledger committed + refunded |
| Retry after a confirmed failure | new claim → `done`, 64; usage 2 in total |
| Failure update fails (mock) | 502 still returned; no save attempted |
| Release unknown (mock) | candidate still leaves `analyzing` (no result can land later); unconfirmed copy |
| Browser after 502 (context test) | fenced release with localized copy; batch continues; if the server already set `error` (release → false) the reload shows `error`, no loop |
| Fence write lost + browser gone | **M2-D3 stale recovery** reclaims after the lease without `needs_confirm`, because the prior reservation is `refunded` (real DB) |

## 7. Personal recovery and the lost-502 limitation

| Case | Result |
|---|---|
| Invalid before save | no history row (server); the browser never upserts a non-200 result (context test, incl. mixed batch) |
| Confirmed release | `quotaReleased: true` copy |
| Release failure / unknown | unconfirmed copy (unit) |
| Response lost after a successful release | browser gets no HTTP answer → M3-A lookup by key finds no row → existing "may still be saving" copy (context test pins it) — **known debt** |
| Duplicate submission | 409 `state: refunded` (real DB) |
| History reload | owner reload equals body (real DB) |
| Recruiter lost 502 | effectively resolved: the server-side fence already set `error`; a reload shows it |

**Option (not implemented, needs approval):** on lookup timeout, resend the **same key** once; the existing reserve RPC answers 409 `duplicate_request` with the ledger `state` and no Gemini call, so `state: refunded` → "not counted" copy. Limits: (1) a resend while the original is still in flight gets `state: reserved` (still ambiguous); (2) the client's 409 mapping (`aiErrorDuplicateRequest`, "check History") needs a code+state mapping; (3) it needs the original request body again. Tests would be: context test for resend-on-timeout, DB test for 409 state after refund (exists).
